# Spike: one Qwen3-TTS talker layer in Rust over ggml

**Question.** Can Rust, calling ggml through a thin `-sys` binding, build layer 0 of the Qwen3-TTS talker and get
output bit-for-bit identical to qwen3-tts.cpp's, at the same speed? The Qwen engine needs token-exact parity, and
that rests on this.

**Answer: yes, on CPU.** Byte-identical output, every planted defect but one seen (and that one is a real
equivalence, below), and no measurable speed difference.

## What is here

| Path | What it is |
|---|---|
| `ggml-sys/` | Raw bindings to ggml, generated by bindgen at build time. ggml is the submodule `ggml-sys/ggml` at `af97976`, built by CMake from `build.rs`, or prebuilt archives given in `GGML_LIB_DIR` |
| `layer0/` | The Rust program: loads the talker GGUF, builds layer 0, runs it on a seeded input, writes the output bytes, and times it |
| `reference/` | The C++ harness: the same layer transcribed from qwen3-tts.cpp at `16bb5af`, built against that checkout's own ggml |
| `run.sh` | Builds both, compares them, runs the planted defects, and with `TIMING=1` times both |
| `diff.py` | Byte comparison; on a mismatch, the count, the first differing element and the largest gap |

The layer is `build_prefill_forward_graph` in `src/transformer/transformer_graph_talker.cpp:39-172`, loop body for
layer 0, with the inputs filled as `src/transformer/transformer_runtime.cpp:101-205` fills them. Both programs cite
the line of each op. The op sequence: RMS norm, ×attn_norm; Q, K, V matmuls; reshape; Q and K RMS norm and ×norm
weight; `ggml_rope_multi` (M-RoPE, sections from the GGUF, `[24, 20, 20, 0]`); K and V written to an F16 cache by
`ggml_set_rows`; `ggml_flash_attn_ext` at F32 precision with an F16 causal mask; `ggml_cont_2d`; output matmul;
residual; RMS norm, ×ffn_norm; gate and up matmuls; `ggml_swiglu_split`; down matmul; residual. Weights are Q8_0,
read at their file offsets into a CPU buffer, and run through `ggml_backend_sched` as the reference does.

The model is the published talker, `jmtl/hk-cantonese-cc0-qwen3-tts-GGUF` at tag `v0.0.1` (commit `5a76602`),
`qwen-talker-hk-cantonese-cc0-v0.0.1-q8_0.gguf`, sha256 `33502b20…0b67`. `run.sh` downloads it (2.0 GB) unless
`MODEL` names a copy, and checks the hash either way. No weights are committed.

## Results

Measured on an i9-12900K under WSL2 Ubuntu 22.04, gcc 11.4, CPU only, 4 threads on both sides, 16 tokens, seed
20261106.

**ggml.** qwen3-tts.cpp at `16bb5af` vendors ggml at `af97976c`, the same commit as the submodule here. `run.sh`
refuses to compare if either differs.

**One ggml build for both sides.** `run.sh` builds ggml once, inside the reference harness's CMake build (Release,
static, `-O3 -DNDEBUG -fPIC -march=native -fopenmp`, ggml's defaults otherwise), and the Rust program links those
same three archives through `GGML_LIB_DIR` and binds that tree's headers. The two executables carry the same
compiled ggml, so a difference could only come from the graph each side builds. Separately, with `ggml-sys` building
ggml itself from the submodule with the same CMake options, the output was also identical.

**Identity.** Rust and C++ outputs are byte-identical: 131,072 bytes (16 × 2048 f32), sha256
`f9efdd88…d2d6`. Also identical at 1, 64 and 300 tokens (300 crosses the 256-row padding of the KV view), at other
seeds, and at 1 thread.

**Planted defects** (`--plant` on the Rust side):

| Plant | Result |
|---|---|
| `rope-normal`: `ggml_rope_ext`, adjacent-pair rotation | red: 30,720 of 32,768 floats differ, max abs 0.289; token 0 is identical, as a rotation by position 0 is the identity |
| `swap-gate-up`: `ggml_swiglu_split(up, gate)` | red: all 32,768 differ, max abs 0.870 |
| `norm-order`: ×attn_norm before the RMS norm | red: all 32,768 differ, max abs 5.67 |
| `rope-neox`: `ggml_rope_ext` NEOX in place of the M-RoPE | **identical**, and correctly so |

The last row is a finding, not a blind spot in the comparison. For text, the reference gives all three M-RoPE
sections the same position (`transformer_runtime.cpp:164-180`), and ggml's M-RoPE then rotates exactly as NEOX
does, bit for bit. A wrong rope *mode* between those two cannot be seen on text-only input; a test meant to catch
one needs positions that differ between sections. `run.sh` checks this equivalence stays true rather than
treating it as a plant.

**Speed.** 100 calls after 10 warm-up calls, each call building the graph, allocating it, setting the inputs,
computing and reading the output. Three alternating rounds, median ms per call:

| Round | C++ | Rust |
|---|---|---|
| 1 | 6.206 | 6.051 |
| 2 | 6.024 | 6.098 |
| 3 | 6.004 | 6.187 |

Means 6.08 ms (C++) and 6.11 ms (Rust): a 0.5% gap with the sign changing between rounds, inside the run-to-run
spread. Graph construction through FFI costs nothing measurable beside the compute.

## The binding, and what in ggml's C API fights Rust

**Size.** The hand-written binding is 104 lines: `build.rs` (85), `src/lib.rs` (14), `wrapper.h` (5). bindgen
generates about 3,600 lines with 612 functions from `ggml.h`, `ggml-alloc.h`, `ggml-backend.h`, `ggml-cpu.h` and
`gguf.h`. The layer program calls 65 distinct ggml and gguf functions.

**Unsafe surface.** All of it. Every call is `unsafe`, every tensor is a raw `*mut ggml_tensor`, and the program
is one `unsafe` block plus four `unsafe fn`s. A safe wrapper is the next layer and is not in this spike.

**What fights Rust:**

* **Errors abort the process.** `GGML_ASSERT` calls `abort()`: there is no error return to turn into a `Result`, and
  a panic cannot unwind through it. Seen here: setting an input that the graph does not use (it is absent from the
  graph, so `ggml_graph_get_tensor` returns null) killed the program inside `ggml_backend_tensor_set`. A safe wrapper
  must validate before calling, not after. `ggml_set_abort_callback` exists, but it is called just before the
  abort and cannot cancel it.
* **Lifetimes are implicit.** A tensor belongs to the `ggml_context` that made it, its data to a backend buffer,
  and a graph's metadata to a caller-provided `mem_buffer` reused on every call. None of this is in the types. A
  wrapper needs a lifetime per context (`Tensor<'ctx>`), and graph contexts that borrow their meta buffer.
* **Function-like macros vanish.** `GGML_PAD` is not bound (and the name `ggml_pad` is taken by an op), so the
  binding re-implements it. `static inline` header helpers are not bound either.
* **Array parameters decay.** `ggml_rope_multi`'s `int sections[GGML_MROPE_SECTIONS]` arrives as `*mut c_int`, so the
  length of 4 is not checked, and the pointer is `mut` though ggml only reads it.
* **Plain-int enums and flag macros.** Rope modes are `#define`d `int`s and the backend enums come through as
  integer constants, so nothing stops passing a rope mode where a type is expected.
* **The build is the hard part, not the binding.** bindgen needs libclang and its resource headers (`stdbool.h`):
  with a bare `libclang.so` and no headers it fails, which here was fixed with
  `BINDGEN_EXTRA_CLANG_ARGS=-I/usr/lib/gcc/x86_64-linux-gnu/11/include`. Static linking needs the archive order
  `ggml`, `ggml-cpu`, `ggml-base` and the system `stdc++`, `gomp` and `m`. Rust links position-independent
  executables, so ggml must be built with `-fPIC`; the reference side is built the same way so the flags match.
  `-march=native` makes the build machine-specific, which is right for a parity check and wrong for a release
  binary.

Nothing in the API stopped bit identity: the C API passes floats and ints by value, and Rust's `f32` and `i32` are
the same bits.

## Not tested

* CUDA. The bit-for-bit claim is for the CPU backend; a GPU comparison is the next step.
* Windows and macOS. Run on Linux only.
* More than layer 0, the single-token step graph, the code predictor and the sampler.
* A `-march=native` build compared across two different CPUs. Both sides ran on one machine.
* The harness transcribes the reference's graph rather than calling the reference library, so the claim is that
  Rust over ggml reproduces that graph exactly. That the transcription matches the library's full forward pass was
  not checked by running the library.

## Running it

```bash
git submodule update --init spike/layer0/ggml-sys/ggml
# needs cmake, a C++ compiler, libclang (e.g. apt install libclang-dev clang) and python3
THREADS=4 TIMING=1 spike/layer0/run.sh
```

`MODEL=/path/to/the.gguf` skips the download, and `QWEN3_TTS_CPP=/path` uses an existing qwen3-tts.cpp checkout at
`16bb5af` with its ggml submodule.

This crate is kept out of the main Cargo workspace (`exclude` in the root `Cargo.toml`), so the existing CI jobs
neither build ggml nor need libclang.
